## OpenViking 深读（哲学最同构，值得单独记）

**核心**：上下文不是黑盒向量池，而是 `viking://` **虚拟文件系统**——知识（resources）、记忆（memories）、技能（skills）统一成可 `ls/tree/read/write/grep` 的目录；每个目录带生成摘要，agent 先扫摘要再决定读全文。

**三层上下文**：L0 一句话摘要（快查相关）→ L1 概览（规划用）→ L2 全文（按需）。**与我们 memory v0.2 对照**：我们的"文件即接口 + profile.md 常备页"已是它的雏形——缺的是 L0/L1 摘要层（目前 facts/月度文件只有标题，无生成摘要，recall 直接全文打分）。

**Session 固化**：会话提交后归档为可检查、可编辑、可合并的 markdown 记忆——与我们 TaskLine/evolution.md 同构。**自进化**：上下文库本身随使用自进化（RSI 相关性的来源）。

**取舍**：AGPL-3.0 + 独立服务形态 → 不装服务、不混代码，**吸收三层摘要设计**（第二批记忆后段：给每个记忆文件维护 L0 一句话/L1 概览头，recall 先扫摘要再全文打分——纯 stdlib 可做，L0 由固化 LLM 顺带生成）。

## 对 v2 知识库决策的建议（更新 cap-weknora / cap-pageindex 对比）

1. **自托管平台二选一**仍在 WeKnora（中文/平台级/自定义许可需读）vs khoj（第二大脑品类头部/AGPL）；两者都是服务形态，daemon 经 API 调用
2. **新增候选**：FastGPT（29.8k，国内，许可需读）、KAG/OpenKB（Apache-2.0 最友好，图谱/轻量两路线）
3. **我们的差异化**：记忆层（facts/observations/profile）与知识库**不该合并**——记忆是"助手对用户的了解"，知识库是"用户投喂的资料"；前者自建（已做），后者上平台（v2 提案）。OpenViking 把两者统一在一个文件系统里的思路很美，但对个人助手是过度统一
4. 无论选谁：`docs/` 敏感文件排除是接入红线（宪法不变量 1）
